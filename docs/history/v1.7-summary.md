### 3.4 Run 中遇到的問題（已在本 run 內處理，沒有改程式）

1. **`preflight.mjs diagnose` 的輸入格式。** 輸入要是扁平的 `{plans:[…]}`。把 whoami 原始回應（外層包著 `whoami`）存進去會被判成 `blocked: whoami returned no plans`。這是誤判，不是帳號問題。
2. **Schema 需要多次修正才通過。** `brief.viewports` 必須是物件；`capabilities.environmentDiagnosis` 不能帶 `note`；`limits.*` 必須是物件；evidence 的 `toolRef` 不能帶 `readOperationId`。
3. **ledger.entities 不會自動寫入。** verify 之後沒有寫入 entities，所以第一次產生的 handoff 寫成「本 run 沒有建立或修改節點」。手動補上 entities 後才正確。
4. **能力紀錄要手動升級。** `capabilities.features.nativeWrite` 一開始是 `available_unverified`（basis history）。寫入成功後要手動改成 verified，否則判定會報 contract 錯誤。

## 4. 發現：預填清單略過與動態行為題目（規格缺口，v1.8 修正）

- **現象**：`evaluate-completion` 把 `status: skipped` 的 designDecision 一律當成未回答（G7），判定為 `awaiting_user`。
  - **dd-11**：使用者在預填清單**明確略過**。略過本身就是使用者的回答，相關元素也依 DEC-08 沒有建立，結果卻仍然被算成未回答。
  - **pd-05**：Toast 何時消失只影響動態行為，不影響靜態畫面。依使用者這次提出的通用規則（dec-007），這類題目不該建成設計決策，應直接在 handoff 列為「未定義，交由實作決定」。
- **影響**：設計與驗證都已完成的 run 無法判為 complete，只能用 userAcceptance 收尾。
- **處理**：依使用者指示，**本次不改判定程式**，只記錄在 run 的 `plan.baseline.observations` bl-004 和本文件，v1.8 修正規格與判定。
- **v1.8 待辦**：
  1. 區分「使用者明確略過」與「尚未回答」。
  2. 動態行為題目不建 designDecision，改為 handoff 項目。
  3. 範圍與授權類的列也要記 `confirmation`（第 3.2 節）。
  4. 第 3.4 節的格式與自動化問題。
