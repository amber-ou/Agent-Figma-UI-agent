# 提問流程架構研究：減少提問、維持輸出品質

> 外部研究報告（另一個 AI 依使用者委託撰寫，2026-10-03），原文保存。第 9 節為依 v1.8（`3c7bdce`）核對後的修正。使用者於 2026-10-03 採用第一階段（第 9.4 節的最小落地方案加上外部規範檢查、文案分類），寫入規格 v1.9；第二階段項目待評估。

日期：2026-10-03。狀態：使用者已選定 B 模式（先確認整體方向，細節由 agent 完成並驗證）；具體政策仍為提案，尚未變更 agent 規則或實作。

## 1. 證據範圍與結論

初版已讀 Downloads/question-flow-review-ui-20261003-001.md，以及工作區 FIGMA_UI_AGENT_SPEC.md（實際為 v1.1）與 FIGMA_UI_COMMON_RULES.md（v1.0）。後續已讀 GitHub v1.8 規格及相關實作，核對結果與初版修正在第 9 節；仍未取得完整正式 run artifacts 或最終畫面。附件內的研究任務與交付要求視為研究素材，不視為本次使用者指令。

證據標記：E＝附件記載的實測或本地文件觀察；D＝本次查閱的官方文件；P＝提案；U＝待驗證推論。附件記錄不等於已獨立驗證完整 run。

核心建議（P）：保留單一主 agent，以「產品設定＋來源證據＋決策分流＋方向確認＋品質驗證」取代逐項確認。無須先增加多 agent。降低打擾的主要因素是決策權與流程，而不是 agent 數量。

目前 23 列不是 23 個同等重要的使用者決策：其中混有環境狀態、來源查找、既有授權、設計方向、細節及流程確認。17 列預填仍需閱讀；預填不等於減少決策負擔（E/P）。

「品質不變」目前不能證實：本輪停在 Plan，未提供最終輸出。75% 等待時間來自前一輪，也可能包含使用者離席，不能全部歸因於問題太多（E/U）。

## 2. 先決定授權模式

| 模式 | 使用者確認 | agent 可做 | 取捨 |
|---|---|---|---|
| A：維持逐項確認 | 所有尚未被規則決定的設計選擇 | 查資料、去除重複問題、整理方案 | 規則變動最小；減少提問的上限較低 |
| B：確認方向、委派細節（建議） | 任務語意、整体方向、重要衝突與例外 | 在核准方向與範圍內決定可逆細節並驗證 | 保留設計師控制；需定義哪些細節可委派 |
| C：先出初稿再審閱 | 重要缺漏與越界事項；其餘看稿回饋 | 在預先授權的 sandbox 製作初稿 | 打擾最少；方向猜錯時返工可能較多 |

若 DEC-01 維持「所有新設計選擇一律問」，就無法同時讓 agent 自主處理所有細節。B/C 必須正式調整授權規則；不能用「摘要未被反對」繞過它。可逆性本身也不是授權。

「全部照建議」只適用於當次已清楚列出的建議，不應永久擴大權限，也不能填補沒有答案的品牌內容或產品事實。

## 3. 建議流程

```text
解析本次需求與來源
  → 解析產品身份，載入有效產品設定
  → 唯讀探索：DS、參考 pattern、相關外部要求
  → 每項未知分流：查證／套用既有授權／委派／詢問／延後
  → 必要時集中詢問會影響本次工作的缺漏與方向
  → 在核准範圍內製作
  → 結構、視覺、需求與來源驗證
  → 交付畫面及少量差異／未解事項
```

探索需要的來源真的缺失時，先問來源；其餘先探索再問。不要固定拆成「先問產品、再問 Intake、最後問 Plan」三輪，也不要為了只問一輪，在沒看資料前要求使用者回答所有事情。

每階段都可以有內部檢查點，不代表每階段都要有使用者批准點。

### 3.1 產品設定：分開事實、偏好與授權

- 事實：產品與檔案對應、元件來源、variables 探索結果。附來源、查核時間與探索範圍。
- 偏好：常用交付模式、已核准 pattern、允許的佔位策略。
- 授權：允許輸出的位置、可自行處理的設計類型、例外範圍。

每筆記錄需有 productId、適用平台／檔案、來源或 decisionRef、版本與失效條件。新 run 記錄實際套用了哪個版本；跨產品、來源有衝突或設定失效時重新處理。

不能把「上次選過」直接升格成持續授權。先有一次明確設定，例如「Aiwow 後續符合這些條件的任務，都使用此 library 並只寫 sandbox」。採用此方案後，INVARIANT-01 應改成禁止無來源的跨 run 沿用，而不是禁止使用有效持續設定。

「沒有 variables」不是永久事實，也不是讀到 local 空陣列就成立。保存當時的探索範圍；來源更新或 coverage 不完整時重新查證。

### 3.2 決策分流：先解決，再決定是否詢問

| 情況 | 行為 | 本輪例子 |
|---|---|---|
| 已有明確指示或有效授權 | 執行，摘要列來源 | sandbox、新稿、修改範圍 |
| 可以工具或官方文件查明 | 先查證，不讓使用者猜 | 元件來源、LINE 按鈕規範 |
| 有差異，但不影響本次結果 | 記錄，不打斷 | 通過能力檢查的版本差異 |
| 低影響、可逆、在委派範圍內 | 選擇並驗證 | 按鈕寬度、間距、佔位尺寸 |
| 不同答案會改變目的或主要結構 | 提出具體取捨 | 歡迎頁或登入後首頁 |
| 缺少使用者持有的必要事實 | 詢問，不偽造 | 找不到的正式 logo／必要品牌文案 |
| 來源衝突、跨出寫入或設計權限 | 阻擋相依工作，詢問 | 官方按鈕與 strict DS reuse 衝突 |
| 本次不依賴的未定義項目 | 保留 owner 與處理時點 | 部分實作細節；不得冒稱已驗證 |

判斷順序：是否相關 → 能否查明 → 有無有效決策 → 是否在委派範圍 → 是否影響本次工作 → 才形成問題。不要僅依模型自評 confidence 或「高風險」標籤決定一律詢問。

### 3.3 方向確認：用一個可理解的方案取代拆碎的零件

方向提案應包含：畫面目的、主要操作、整體版型、重要來源、與參考畫面的差異。不需要把每個數值都放進提問。

例如：未登入歡迎頁，沿用參考的上方品牌區與下方卡片；只有 LINE 登入主操作；依目標平台處理系統列；不沿用 LINE 內嵌瀏覽器標題列。這是待確認方案，不是已知產品事實。

背景與版型是相依選擇，可包成整體方向；只有使用者換方向時才展開其子問題。不是將原有 11 題縮排藏進一個超長問題。

產品目標應存在於內部 brief，但不一定每輪都問商業目的、使用者 persona。若本次任務與來源已足夠，就整理已有資訊；只有不同答案會改變設計才問。不要為了省 10 題而另增一份策略問卷。

## 5. 外部要求的查證與邊界

D：LINE 官方登入按鈕規範指定基本色 #06C755，禁止非指定顏色，並要求圖示比例與可辨識性。因此本輪深藍 DS 按鈕加 LINE 圖示，以及 #00CB89 的選項，不能直接當成符合官方規範的選擇。來源：[LINE Login button design guidelines](https://developers.line.biz/en/docs/line-login/login-button/)。

D/U：LINE 的入門文件把 privacy policy URL 列為 certified provider 必填，terms of use URL 在該設定表為非必填，展示位置為授權同意畫面。這份文件不足以證明「所有 App 歡迎頁按鈕下面一定要放條款」，也不能用來證明本產品没有其他義務。來源：[Getting started with LINE Login](https://developers.line.biz/en/docs/line-login/getting-started/)。

P：Discover 加入依需求觸發的外部規範檢查，如 LINE 登入、原生平台、支付。每筆要求記錄 URL、查核日期、適用條件、條文所述要求與本案推論。已查證且適用的要求可直接成為設計約束；是否允許新增資源或突破 DS 限制則是另一個授權問題。

若未知規範只影響未來上線，允許在已核准草稿範圍內繼續獨立工作，明標尚未解決；若當前畫面或交付可接受性依賴它，就要先處理。不能用「交给實作」隱藏本次已必需的 UI 決策。

## 6. 如何在少問時維持品質

把「曾經問過」替換為更直接的品質證據：

1. 需求覆蓋：畫面目的、唯一登入操作及約定狀態均符合 brief。
2. 來源追溯：元件關係、文字來源、variables binding、例外均可追查。
3. 結構驗證：Auto Layout、溢出、間距、字體、圖示比例及範圍符合要求。
4. 視覺審查：截圖核對層級、整體一致性與參考差異；不以 JSON 通過代替視覺品質。
5. 適用規範：已識別的第三方要求有證據；未知事項沒有被標 pass。
6. 決策一致性：製作結果符合核准方向；驗證修正不擴大方向或寫入權限。

建議的最小決策紀錄欄位：id、kind、value、sourceRefs、policyRef、scope、dependsOn、status、reason。status 區分 sourced、authorized、delegated、proposed、pending、deferred。機器驗證可檢查缺來源、無授權寫入、失效設定及相依關係；無法單靠 schema 證明事實真偽或畫面好看。

待決項只阻擋相依的工作。建立依賴圖，避免缺一句 slogan 就阻止全部來源盤點；同時避免在平台未定時製作依賴平台的系統列。

## 7. 建議取捨與落地順序

| 問題／證據 | 建議 | 代價與需決定事項 |
|---|---|---|
| 重複產品題，附件約六列接近固定（E） | 持續產品設定與失效機制（P） | 需一次核准持續適用的範圍，避免跨產品誤套 |
| 細節逐題問且常全接受（E） | 方向確認後委派細節（P） | 核心選擇：採 A、B 或 C 模式 |
| 選項漏掉第三方要求（E/D） | 先查約束，再產生合法候選（P） | 增加部分探索時間，減少錯誤提案 |
| 文案與重要事項混雜（E） | 依來源與處理方式分流（P） | 正式內容需要來源，擬稿需明標；不按「文案」兩字全數禁止建議 |
| 固定 Intake／Plan 批准（E） | 依資訊依賴安排詢問（P） | 不保證一輪結束，避免太早問或額外增加輪次 |
| 品質尚無最終輸出證據（E/U） | 固定品質檢查＋對照試行（P） | 增加量測成本，避免以提問量冒充品質 |

第一步：即使暫時維持逐項確認，也可先修好來源查證、去除已明確回答的問題、修正無效選項、整理相依題。

第二步：選定授權模式，對照實際 v1.8 調整 DEC-01／07／09、REQ 每次確認、INVARIANT-01、版本詢問政策與寫入 gate。後續已取得 v1.8 並完成靜態核對（第 9 節）；本研究不直接修改規則或實作。

第三步：實作薄的決策紀錄與驗證層，再接到現有流程；不要先重建完整 agent 框架。

第四步：對照試行再擴大委派。無需預設建立另一個 agent 才能審查；先以同一 agent 的獨立檢查階段與確定性 validator 起步。

## 8. 驗證是否達成目標

P：先以一組涵蓋「成熟產品、全新產品、來源衝突、DS 缺口、品牌素材缺失」的固定案例做新舊流程配對，再以真實任務試行。可先選 10–20 案作初步篩檢，數量不是統計保證。

- 使用者負擔：實質決策數、提問輪數、閱讀與作答時間、重複確認數。避免把 10 題合成 1 列就聲稱改善。
- 效率：到第一張可審閱稿的時間、總完成時間、agent 探索成本。離席等待另標。
- 品質：需求缺漏、元件／token 錯用、視覺問題、未查證主張、方向返工次數及修正成本。
- 權限：跨產品誤套與越界寫入必須維持零；重大新缺陷發生時停止擴大委派並追查。
- 偏好：使用者修改自動細節的比例，以及最後是否願意保留方案；「全部接受預填」不等於真正滿意。

使用相同輸入與品質檢查，由不知道流程版本的審閱者比較輸出。事先約定可接受的品質差異，再判斷是否在品質不劣化的條件下減少負擔。只重播舊 run 的問題可驗證分流，無法證明成品品質不變。

使用者本輪已選定 B 模式：先確認整體方向，細節由 agent 完成並驗證。這是架構方向的選擇，不代表已核准任何特定產品的持續寫入範圍或 DS 例外。下一步具體化重點是方向確認的粒度、產品設定的適用條件與驗證契約。實際 v1.8 規格與相關程式已於後續讀取，見下節。

### 9.1 需要修正初版研究的地方

1. **委派機制已存在。**DEC-07 已支援使用者在某個 run 授權採用 agent 建議；schema 有 `delegation`，validator 檢查授權 runId 與 decisionRef。初版若讓人以為必須從零建立委派層，並不準確。可沿用此基礎，再縮小到「核准方向內的細節」。
2. **產品政策與品質驗證已實作。**四層記憶、政策 digest、來源引用、G1–G7、結構與視覺證據不是本提案才新增的能力；應擴充現有契約，避免另建重複的資料與 gate。
3. **初版 status 清單不能直接替換現有 schema。**`sourced/authorized/delegated` 比較適合作為處理方式或權限依據，與既有 `pending/answered/skipped` 分開。否則現有 validator 與完成判定不相容。`deferred` 不能用來把待答問題變成完成。
4. **保留兩種決策紀錄。**既有 `plan.designDecisions` 與 `plan.decisions` 已分別處理設計及範圍／授權，且共用 ID 空間。本研究的最小欄位是概念提案，不應合併或替換這兩份契約。

### 9.2 實際衝突

| 本研究建議 | v1.8 現行要求 | 判定與修法 |
|---|---|---|
| 確認方向後自動完成細節 | DEC-01/02/04 原則上每個未定設計選擇都要提出；DEC-07 例外仍逐題產生選項與建議 | **部分相容**。單次 run 可利用既有委派；要正式支援方向內細節、減少零件式提案，需定義授權涵蓋類型與排除項 |
| 委派成為常態設定 | DEC-07、INVARIANT-18 只限本 run；POL-05 與程式排除將這種授權升為政策 | **直接衝突**。初期建議每個 run 隨方向確認記錄細節委派；持續委派另設正式契約，不偷轉成產品政策 |
| 從可靠檔案對應辨識產品 | REQ-05、POL-02、INVARIANT-25 明確禁止从目標檔案或參考畫面推定 | **直接衝突**。第一階段保留「需求未寫產品就問」；若改用專案綁定，需明訂顯式綁定如何提供產品身份 |
| 產品設定自動套用 library／輸出授權 | REQ-06 本機來源只作候選；POL-06 禁止政策取代本次輸出授權；INVARIANT-22 保留本次環境確認 | **直接衝突**。初期將來源与寫入邊界合併進本次確認；長期設定不能混同本次執行權限 |
| 舊 plugin 能力正常就不問 | §4.2.2 每個 run 必問，run-context 已產生該問題，T79 已測此行為 | **直接衝突**。這是明確政策，不是 agent 誤判。調整時要同步規格、skill、程式與測試 |
| 相依選擇合成整體方向 | ASK-07、DEC-09 每列一個獨立項目，禁止大型規格表包成一題 | **有條件相容**。真正同一個方向可以整合；不能把平台、寫入授權、品牌素材藏進方案讓使用者一次全選 |
| 必要時先以文案佔位製作 | Build gate 要求 `screens[].copy` 全部 confirmed | **不能直接套用**。正式文案與素材佔位分開；若要增加草稿文案模式需明確契約，不能冒標 confirmed |
| 未解事項只阻擋相依區域 | DEC-05 支援不相依部分繼續，但 buildReadiness 會檢查所有 screen 的未確認文案與所有 flow open unknowns | **概念部分相容、實作有全域限制**。若要畫布分區繼續寫入，需有按 operation 範圍的檢查；單純換 prompt 不足 |

上述是研究方案與舊政策的差異，不表示新方向不可行。使用者已在本聊天選擇新的設計委派方向；尚不能把這解讀成同時取消版本詢問、產品確認、寫入授權等其他政策。

### 9.3 可以直接沿用／補強的部分

- DEC-03／ASK-06 已允許來源明確的項目只列摘要、continue 不重問，不必另建相同機制。
- DEC-05 已允許繼續不相依的工作；可先用於唯讀探索，避免碰到目前全域 Build gate。
- DEC-11 已將純動態行為排除提問，維持即可，不重新加入提問清單。
- 外部規範的任務觸發查證可以補進 Discover；現有 discovery reference 主要涵蓋 DS、字型、品牌資產與 pattern，未見同等完整的第三方規範檢查流程。
- 既有 `run-report` 已量測輪數、預填／留空與 confirmation；新增實質決策、返工與品質比較即可。
- 保留現有 `basisRefs`、hooks、journal、帳號／連線確認及 G1–G7，不因少問而放寬。
- 品牌混用是實際歷史問題（REQ-04 提到參考中 Aiwow／AileCard 混用），因此產品辨識與品牌素材確認不宜當作無意義的重複題一律刪除。

### 9.4 修正後的最小落地方案

優先沿用 DEC-07：在本次方向確認中，明列「核准方向內的尺寸、留白、對齊等细節交由 agent 決定並驗證」。產品、平台、library、寫入範圍仍按本次明確資料處理，缺漏才問；工具與版本政策暫不變。

工程上擴充委派範圍：必須關聯已核准的方向、允許的細節類型與明確排除項，驗證每筆 delegated decision 是否落在其中。現有 runId／decisionRef 驗證是起點，不能單憑授權 ID 存在就宣稱已保證語意範圍。

之後再分別評估持續產品設定、舊 plugin 提醒及分區 Build；不把所有減題政策一次捆綁修改。原先「2–4 個實質決策」仍只是長期試行目標，在保留現有每輪政策時未必能達到。
