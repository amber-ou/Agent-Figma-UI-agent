# 提問方式與方向制定：run `ui-20261003-001` 的問題整理（研究用）

日期：2026-10-03 · 對應規格：`FIGMA_UI_AGENT_SPEC.md` v1.8 · 性質：研究素材，**不是規格**

這份文件給負責研究的 agent 使用。內容是第一次正式需求（不是測試回合）中，agent 實際提出的所有問題，以及目前規範這些問題的規則。研究目標：評估目前「制定設計方向」與「詢問使用者」的架構和方式，有沒有可以優化的地方。

- 資料來源：使用者轉貼的本機 agent 回覆。初版寫於 Plan 階段；第 3.4、3.5 節為之後補上的使用者回覆與 Build 階段新增的題目。run 尚未完成交接。
- 標記方式：**事實**是 agent 實際的輸出；**觀察**是審查者（雲端 session）的看法；**假設**是尚未驗證的推論。
- 研究結果若要變成規則，必須先由使用者確認，再修訂規格（規格是唯一規範來源）。

## 1. 需求與背景

使用者的原始需求（一句話）：

> 依照目前畫面 產出 app 的首頁 按鈕只會有使用 line 帳號登入

背景：
- 產品是 Aiwow 電子名片（LINE OA）。已有產品政策：對比規則不適用（`product-policies/aiwow.json`）。
- 元件 library 是 Aiwow Library，**沒有 variables**（長期缺口 gap-001）。
- 寫入只能在測試檔的 figma-ui sandbox 頁。
- 使用者是設計師。之前的測試回合大多回覆「其餘照預填確認」或「全部照建議」。

## 2. 目前的提問規則（摘要）

研究時要遵守的前提。若某條規則本身就是問題，請提出修改建議，不要直接忽略：

| 規則 | 內容 | 規格位置 |
|---|---|---|
| 設計決策一律問 | DS、既有 pattern、產品政策或使用者指示沒有決定的外觀、層級、體驗選擇，agent 不得自行決定。不確定算不算時，當作是 | §7.4 DEC-01–05 |
| 預填清單 | 同一階段的待決項目一次列成清單。有建議的填好並標「建議，請確認」；沒有建議、或屬品牌、產品方向、文案、個資的留空。確認前一律是 pending | §7.4 DEC-09 |
| 產品政策題優先 | 對比這類「整個產品是否遵循某規則」的題目，每個產品只問一次 | §7.4 DEC-10、§7.5 |
| 動態行為不問 | 只影響動態行為的問題不問，交接時列為「未定義，交由實作決定」 | §7.4 DEC-11 |
| 使用者略過 | 使用者明確略過算已解決；agent 標記的略過仍算待答 | §7.4 DEC-08 |
| 每次確認需求 | 產品、平台、library 每個新 run 都要確認；產品沒寫就問，不從上次 run 推定 | §7.1 REQ-01、05、06 |
| 元件與 variables 分開確認 | 核准元件 library 不等於核准 variables | §6.1 |
| plugin 版本 | 本機 plugin 比官方最新版舊時，每個 run 的第一題都要問 | §4.2.2 |
| 減少重問 | continue 沿用已確認範圍；已由 DS、pattern 或指示決定的只列摘要 | §7.2 ASK-06 |
| 溝通語言 | 一律繁體中文 | §7.2 ASK-08 |

## 4. 觀察到的問題（給研究者的起點）

以下是審查者的整理，不是結論。請驗證、補充或反駁。

### A. 重複問「每次都一樣」的事

1. plugin 版本、產品、元件 library、variables library、輸出位置在同一產品的 run 之間幾乎不變，卻每次都要問或確認。
2. 規格的本意是避免 agent 自己沿用上次的選擇（INVARIANT-01），但結果是使用者每次重答相同內容。
3. 已有的機制（產品政策、本機產品檔 `.figma-ui/products/<product>.local.json` 的預填候選）沒有被充分利用。

### B. 預填建議的品質

1. **越界預填**：dd-07 的 slogan 屬文案內容，dd-08 的條款涉及法規與上線要求，規則都要求留空或標明使用者專屬，agent 卻給了建議。
2. **選項不完整**：dd-03 缺少外部品牌規範（LINE 官方登入按鈕）的選項。Discover 只盤點 DS 和參考畫面，沒有「第三方品牌或平台規範」這一步。
3. **預填不是單一答案**：第 7 題的預填寫「A 或 B」。
4. **偏向照抄參考畫面**：dd-02 推薦照抄寫死的漸層顏色。和現有畫面一致是合理理由，但也代表 DS 缺口一直沒被處理。

### C. 使用者可能「全部照建議」

1. 使用者在測試回合多次回覆「全部照建議」。如果正式需求也這樣，預填建議實際上就等於 agent 在做決定，只是多了一次確認。
2. 清單沒有區分影響程度：「按鈕撐滿 358」和「LINE 按鈕是否合規」「條款要不要放」放在同一張表、同樣格式。
3. **假設**：高影響的題目（品牌合規、法規、上線阻礙、會造成例外的 raw 值）如果用不同標記，或不給預填，使用者比較不會一眼帶過。

### D. 清單結構

1. **相依題目**：dd-02 只有 dd-01 選 A 才需要，卻並列。
2. **層級混雜**：S1、S2 是結構與元件來源，dd-* 是設計決策，P 是流程確認，全部放在同一張表。
3. **時間點**：Intake 一次問 12 題，但產品（第 2 題）一確定，產品政策和本機產品檔就能預填其他題。**假設**：先問產品再出清單，可以減少留空列。
4. 需求裡的歧義（「首頁」是哪一種頁面）處理得好（第 10 題），可以當作範例。

### E. 方向制定（Plan 之前）的架構

1. 目前方向由三個來源推導：DS、參考畫面的 pattern、使用者回答。沒有「產品目標或使用情境」層級的輸入，例如這個首頁的商業目的、目標使用者。
2. 參考頁沒有現成的 App 首頁，agent 拿最接近的「04-01 宣傳頁面」當版面基準。這個類比是 agent 的判斷，以 dd-01 選項呈現，但沒有說明為什麼選這頁、還有哪些候選。
3. 外部限制（LINE 登入規範、法規、平台規範）沒有固定的檢查點。

### F. 和提問無關、但影響體驗的事

1. capabilities 和 inventory 的格式各被 schema 擋下一次才通過。v1.8 原本要讓錯誤訊息直接給出正確格式，看起來還不夠。
2. 等待使用者的時間占大部分（v1.7 約 75%）。提問次數和清單長度直接影響總時間。

## 5. 請研究者回答的問題

1. **哪些題目可以不問**：哪些可以改成「預填並在摘要列一行、使用者不反對就算確認」？要守住的底線是：不得由 agent 自行決定設計（DEC-01）、不得悄悄沿用上次 run 的選擇（INVARIANT-01）。請提出能兩者兼顧的做法，例如把「同一產品長期不變的事實」放進產品政策或本機產品檔，並說明它和「每次確認」規則的關係。
2. **預填的邊界**：哪些類型的題目不該預填（文案、法規、品牌合規、上線阻礙、會造成例外的 raw 值）？要怎麼讓 agent 穩定遵守（規則文字、清單欄位、validator 檢查）？
3. **影響程度分級**：清單要不要依影響程度分組或標記？高影響題目要不要強制使用者逐題回答，不能被「全部照建議」一次帶過？
4. **選項完整性**：Discover 要不要加入「外部規範」檢查（第三方品牌、平台、法規）？要怎麼避免把未驗證的規範寫成事實（INVARIANT-16）？
5. **清單結構**：相依題目、不同層級（結構、設計、流程確認）要不要分開？最適合使用者一次回覆的格式是什麼？
6. **提問時機**：Intake 要不要拆成「先問產品」和「再出清單」兩步？Plan 的設計決策能不能提前到 Discover 結束後一次問完？Build 中途才發現的問題（例如 dd-11 的字型）要怎麼在 Discover 就攔下，避免 Build 期間停下來提問並長時間持有寫入鎖？
9. **「放不放」與「寫什麼」**：像 dd-08 這種「要不要放某段文案」的題目，答案「放」之後，文案內容要怎麼處理才不會被題目裡的舉例取代？
7. **方向制定**：要不要在 Plan 之前加入產品目標或使用情境的輸入？選參考 pattern 時，要不要列出候選與理由？
8. **衡量方式**：用什麼指標判斷優化有效？例如總列數、留空列數、使用者修改預填的比例、等待時間、交付後被要求重做的次數。`run-report.mjs metrics` 已有部分數據。

## 6. 交付格式建議

請研究者輸出：
- 每個建議的**問題 → 證據 → 建議做法 → 取捨 → 需要使用者決定的事**。
- 標明分級：**D** 官方文件、**E** 本專案實測、**P** 設計提案、**U** 未驗證。
- 需要使用者決定的事項，用預填清單格式列出（有建議的填好，需要使用者決定的留空）。
