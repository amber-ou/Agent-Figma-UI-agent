# 延伸規格表研究：先抽規格、再提問，縮小 AI 的自由發揮範圍

日期：2026-09-29 · 對應 spec v1.4 · 狀態：研究建議，**尚未實作、尚未實測** · backlog：S-01～S-07

> **v1.6 狀態（2026-09-29）：**研究紀錄。v1.6 只採用其中「先找候選、每輪 1–3 題、按需處理、不偽造來源」的原則；獨立 `spec.json` 規則引擎、L0–L13 完整抽取、固定三輪與十題政策、`unbasedProperties` 硬門檻**不採用**（見 `docs/history/workflow-simplification-record.md` 階段 C）。


情境：拿到一個 Figma 檔，要延伸既有畫面。目標是讓 AI 在 Build 時**幾乎沒有自己決定的空間**：每個看得到的值都來自「從檔案抽出、使用者確認過的規格」或「使用者的回答」。

本文件回答兩個問題：

1. 要從既有檔案抽出哪些規格，讓使用者確認？（第 3 節）
2. 抽不出來或有疑慮的部分，要問使用者哪些問題、怎麼問？（第 4、5 節）

## 1. 現況與缺口

spec 已經有這些規則：

- REQ-02：能從既有材料推得的，先整理成候選事實，不重複問。
- §6.6：Discover 盤點 2–3 張參考畫面的版面 pattern。
- §7.4：DS、pattern、使用者指示沒有決定的設計選擇，一律問（DEC-01～08）。
- DEC-06：每個 write 要以 `basisRefs` 引用依據。

缺口：

| 缺口 | 後果 |
|---|---|
| 沒有「要抽哪些規格」的完整清單 | 抽什麼靠模型當下判斷，容易漏（第一次任務的 Status Bar 瀏海、說明文字對比） |
| pattern 是逐項記錄，不是一份可整體確認的規格 | 使用者看不到 AI 將依循的完整規則，也無法一次修正 |
| 沒有「政策題」 | 同類問題（DS 沒有的值、raw 值、參考不一致）每次個案重問 |
| `basisRefs` 只到 operation 層級 | 一個 operation 內的個別屬性值是否有依據，無法檢查 |

## 2. 研究依據

- **D：**LLM agent 遇到指令缺資訊時，傾向**自行補上缺的參數**，因而產生幻覺；讓 agent 在遇到阻礙時發問的框架（Ask-when-Needed）明顯勝過既有方法（Learning to Ask, EMNLP 2025）。
- **D：**即使模型能辨識出請求有歧義，也**很少主動發問**，而是直接假設使用者意圖（Knowing but Not Showing, 2026；同方向的研究多篇）。
- **D：**發問時機與內容可以依不確定性決定：在執行前預測需要澄清之處（Ask-before-Plan）、以資訊增益挑問題（Bayesian experimental design）、依結構化的不確定性引導澄清（Structured Uncertainty guided Clarification, 2025）。
- **D：**設計系統文件的標準結構是：tokens（顏色、字體、間距）、元件規格與使用方式（含 do／don't）、組合 pattern、可及性、語氣與文案、治理規則。一致的空間系統「減少設計者每天要做的決定數量」。
- **E：**第一次真實任務：5 個設計決策中 1 個因沒有候選而被略過；G5 對比問題在 Validate 才發現；Status Bar 瀏海在 Validate 才修正。

**P，推論：**不能靠模型「自己發現哪裡需要問」。應該用**固定的規格欄位清單**逐一填滿（slot filling）：每個欄位不是「從檔案抽出並確認」，就是「問使用者」；沒有第三條路。問題的順序依影響範圍與不確定性排序。

## 3. 要從檔案抽出的規格（延伸規格表）

分 14 類。每一類：要定什麼、怎麼抽（唯讀 `use_figma`）、什麼情況要問。抽出的每條規則附證據（來源節點、出現次數、一致率）。

### L0 任務與範圍（只能問）

| 要定的內容 | 說明 |
|---|---|
| 產品目的、使用者任務、主要 action | 檔案裡沒有，必問 |
| 交付畫面與狀態清單 | 必問；可從參考畫面的命名（例如 `01-04`、`04-11`）建議候選 |
| 輸出位置、新稿或改原稿、可改的節點範圍 | 必問（已在 Intake） |
| 平台與裝置尺寸 | 可從參考 frame 寬度推測，但要確認 |

### L1 參考畫面集合（抽候選 → 使用者選）

- **抽：**依使用者給的頁面或節點，列出候選 frame：同頁、同寬度、名稱相近、instance 組成相似（共同的元件 key 比例）、主要元件相同。每張附截圖與名稱，排序後給 3–5 張。
- **問：**「哪幾張是這次要沿用的標準？有沒有舊版或不該學的畫面？」
- **為什麼重要：**後面所有規則都從這裡抽；選錯參考，規格表整份錯。第一次任務照抄了一張對比不合格的參考畫面。也要記錄**反例**（舊版、廢棄、別的品牌），避免被當成依據。

### L2 畫面骨架

- **抽：**frame 寬高、背景填色（style／variable／raw）、頂部（Status Bar、瀏海或動態島區、Top bar 元件與 variant）、底部（tab bar、home indicator、固定按鈕區）、安全區留白、捲動區域（`overflowDirection`、固定元素）。
- **問：**參考畫面之間不一致時（例如一張有 tab bar、一張沒有）。

### L3 間距與對齊

- **抽：**左右邊距、內容寬度、區塊間距、區塊內間距、元件間距的**數值分佈**，以及每個值綁定的 variable；`layoutGrids`；主要內容的左邊界。
- **輸出規則範例：**「頁面左右邊距 16（Space/400）」「卡片之間 12」「卡片內距 16／20」。
- **問：**分佈不集中（同角色出現多個值）、值沒有綁 token、只出現一次。

### L4 字體排印

- **抽：**每個文字角色使用的 text style（依位置與字級推測角色：頁面標題、區塊標題、內文、說明、按鈕、連結、數字）、字型家族、對齊、行數與截斷設定（`textTruncation`、`maxLines`）、字型是否已安裝（v1.4 §10.3）。
- **問：**同一角色有多個 style、角色推測不確定、該 style 對背景對比不足（v1.4 預檢）、字型未安裝。

### L5 色彩角色

- **抽：**每個角色的 paint style／variable：頁面背景、卡片背景、主要文字、次要文字、強調色、連結、分隔線、錯誤、成功、警告、停用；variable 的 mode；**raw 值清單**（沒有 token 的顏色與漸層）。
- **問：**raw 值是否可以沿用（政策 P-3）；本次需要的狀態色在參考中沒出現。

### L6 形狀與裝飾

- **抽：**圓角值、邊框、effect styles（陰影）、漸層、插圖、背景裝飾在參考中**有沒有出現、出現在哪**。
- **問：**新畫面要不要用裝飾（DEC-02 必問項）；參考有用，但新畫面的角色不同時。

### L7 元件對應

- **抽：**每個語意元素（主按鈕、次按鈕、輸入框、列表列、卡片、toast、top bar…）→ 元件 key、variant、來源（既有 instance 或 library 最新版，v1.4 §6.2）、屬性合約（backlog U-05）、每個畫面的使用數量（例如主按鈕最多 1 個）與位置（例如固定在底部）。
- **問：**同一語意有多個候選元件；新舊版本外觀不同；本次需要的元素在 DS 中找不到。

### L8 組合 pattern

- **抽：**頁首、卡片、列表、表單欄位、dialog、toast、空狀態、底部按鈕列等組合的量測值（沿用 §6.6 與 inventory `patterns`）。
- **問：**本次畫面要用哪些 pattern；參考之間矛盾。

### L9 內容與文案

- **抽：**詞彙表（名詞、按鈕動詞，例如「返回」「確認」「分享」）、品牌與產品名稱、標點（全形或半形）、數字、日期、金額格式、各角色的文字長度（最長、平均）。
- **問：**品牌名稱（REQ-04）、語氣、新文案、超過參考長度時的處理（政策 P-7）。

### L10 圖示與圖片

- **抽：**圖示來源（icon 元件集與使用的 variant）、尺寸、線條或填色風格、顏色 style；圖片的比例、圓角、裁切方式。
- **問：**需要新圖示時，先從 icon set 找 2–3 個候選再問（backlog D-05）。

### L11 狀態呈現

- **抽：**參考中 loading、empty、error、success、disabled 的呈現方式（toast、頁內訊息、整頁狀態、skeleton 或 spinner）與使用的元件。
- **問：**本次需要哪些狀態；參考中沒有範例的狀態要做成畫面、只寫規格，還是不做（政策 P-8）。

### L12 互動與導覽

- **抽：**返回方式、按鈕的目的頁（若參考畫面有 prototype 連線，讀 `reactions`）、toast 顯示時間（若有註記）。
- **問：**目的頁與行為（第一次任務的 handoff 仍留著「按鈕目的頁、Toast 顯示時間未定」）。

### L13 品質底線

- **抽：**參考畫面的文字對比、點擊區量測結果，列出不合格項。
- **問：**不合格的參考要用哪個替代 style（v1.4 §9.5；照抄不能當作合格）。

## 4. 政策題：先定規則，減少個案提問

很多個案問題屬於同一類。**在確認規格表時一次問政策**，之後的個案依政策處理，不再逐一問。政策只對本 run 有效（INVARIANT-01），新 run 可以顯示上次的政策供使用者選擇沿用（REQ-01 已允許「沿用上次設定」）。

| ID | 情況 | 選項 | 建議 |
|---|---|---|---|
| P-1 | 參考畫面之間不一致 | a. 出現次數明顯較多者為準（例如 ≥ 2/3）並列出；b. 一律逐項問 | a（僅供參考） |
| P-2 | 需要 DS 沒有的值（間距、字級、顏色） | a. 一律問；b. 取最接近的既有值並標記；c. 禁止，改做法 | a |
| P-3 | 參考中的 raw 值（例如沒有 token 的漸層） | a. 可照抄並記為例外；b. 不可用 | 看產品，需問 |
| P-4 | 新元件、新 token | a. 禁止（strict，預設）；b. 允許但每次問 | a |
| P-5 | 參考的文字對比不合格 | 換同系列、對比足夠的 style（照抄不合格，G5 無法豁免）；問的是**換成哪一個** | 由規格表列出候選 |
| P-6 | 元件版本 | a. 跟既有畫面（從 instance 取主元件）；b. library 最新發佈版 | a（與參考一致） |
| P-7 | 文字超過參考長度 | a. 換行；b. 截斷（加 …）；c. 縮短文案並問 | 依角色：標題 c、內文 a |
| P-8 | 參考中沒有範例的狀態 | a. 做成畫面並問呈現方式；b. 只寫規格；c. 本次不做 | 依交付清單 |
| P-9 | 平台慣例與參考衝突 | a. 以參考為準；b. 以平台為準 | a（延伸以產品一致為先） |
| P-10 | 設計決策委託（DEC-07） | a. 每題都問；b. 本 run 採用建議（無建議者略過） | 由使用者決定 |

## 5. 提問的方式與順序

### 5.1 三輪提問

| 輪次 | 時機 | 內容 | 目的 |
|---|---|---|---|
| 第 1 輪 | Intake | L0（任務、畫面、輸出位置）＋L1（選參考畫面、反例） | 決定抽規格的範圍；範圍小，後面的抽取才準也才快 |
| 第 2 輪 | Discover 之後 | **延伸規格表**（L2–L13）＋政策題（P-1～P-10） | 使用者一次確認所有規則；有錯直接指出編號 |
| 第 3 輪 | Plan | 規格與政策仍無法決定的個案設計決策（DEC），附候選與並排視覺選項（D-05） | 只剩真正需要設計判斷的題目 |

### 5.2 規格表以「異常優先」呈現

每條抽出的規則依證據分級（門檻是專案預設，可調整，未經實測）：

| 信心 | 條件 | 呈現方式 |
|---|---|---|
| 高 | 在 ≥ 3 處出現、一致率 ≥ 90%、有綁 token 或 style、品質檢查通過 | 摺疊成摘要，整批確認 |
| 中 | 2 處出現，或一致率 70–90% | 逐條列出，需確認 |
| 低／衝突 | 只出現 1 次、一致率 < 70%、raw 值、品質不合格、參考互相矛盾 | 轉成問題，附選項與節點連結 |

使用者的回覆方式：「全部確認」，或「L3-2 改成 20、L5-4 不要用」。這樣第 2 輪是**一次**確認，不違反 ASK-02 每輪 1–3 題的精神；但 spec 需要補充說明規格表確認算一題（backlog S-02 的決策）。

### 5.3 問題排序

同一輪內，影響範圍大、不確定性高的題目先問：

- 影響範圍：受影響的元素數量、跨幾個畫面
- 不確定性：信心等級、候選數量
- 相依：先問的答案會讓後面的題目消失（例如先定 P-6 元件版本，版本差異的個案題就不必問）

### 5.4 每一題的格式

沿用 DEC-04：情境 → 為什麼檔案無法決定（附證據與節點連結）→ 2–3 個選項與差異 → 建議（標明僅供參考）。新增兩個要求：

- 每個選項都標出是否影響硬性門檻（例如對比）。
- 題目要能讓答案**直接變成一條規則**，不是只回答一個個案（例如問「DS 沒有的間距要怎麼處理」，而不是「這裡的間距要 18 還是 20」）。

## 6. 讓規格真的限制輸出

規格確認之後，要讓它**可檢查**，不是只寫在文件裡：

1. **規格檔**：新增 `spec.json`（或放進 plan），每條規則：`id`（例如 `L3-2`）、`layer`、`statement`、`value`、`tokenRef`、`evidence`（nodeIds、occurrences、consistency）、`confidence`、`status`（`extracted | confirmed | changed_by_user | rejected`）、`source`（`file | user | policy`）。
2. **凍結**：確認後的規格在本 run 內凍結；要改需要一筆 decision（和 plan 相同）。`continue` 沿用；新 run 重新抽取與確認。
3. **引用**：write operation 的 `basisRefs` 可以引用規則 ID；validator 檢查引用的規則都是 `confirmed`。
4. **逐屬性檢查**（與 backlog D-02 設計 lint 合併）：Validate 時對每個新節點的可見屬性（尺寸、間距、顏色、字型、圓角、效果、元件與 variant）檢查是否有依據：
   - 符合某條已確認規則，或
   - 來自使用者回答的設計決策，或
   - 是 DS 元件 instance 內部未覆寫的預設值。
   其他都是「自由發揮」。新增指標 `unbasedProperties`（沒有依據的屬性數），完成前必須為 0，或逐項登錄為 finding。這把「縮小 AI 規則範圍」變成可以量測的數字。

## 7. 套用到第一次真實任務（回顧推演，未實測）

若第一次任務（名片分享成功）有規格表，預期可以提前處理的問題：

| 第一次任務的問題 | 會在哪裡被處理 |
|---|---|
| 說明文字對比 3.34:1 | L4／L13 抽取時標為「品質不合格」，第 2 輪就列出替代 style（P-5） |
| Status Bar 瀏海不一致 | L2 骨架規則「頂部為 Status Bar（含瀏海）」，Build 前已確認 |
| 成功圖示沒有建議而被略過 | L10 先從 icon set 找候選，第 3 輪附候選提問 |
| 漸層是 raw 值 | L5 raw 值清單 ＋ P-3 政策一次決定 |
| 新舊 Button 結構不同 | L7 版本來源 ＋ P-6 政策 |
| 按鈕目的頁、Toast 時間未定 | L12 在第 2 輪列為待答，而不是 handoff 才列 |

第 2 輪規格表的呈現範例（節錄；style 名稱、數值與條數都是示意，不是第一次任務的實際資料）：

```text
【延伸規格表 ui-20260928-001】參考：01-04、04-11（反例：無）
需要你確認的（3）
  L4-3 說明文字 style「Body/Caption」對白底對比 3.34:1，不合格。
       候選：Body/Secondary（5.2:1，同系列）｜Body/Default（12.6:1）　建議：Body/Secondary
  L5-6 背景漸層沒有 token（raw 值，2 處出現）。→ 政策 P-3：可照抄並記例外／不可用？
  L12-1 「返回我的名片」的目的頁？參考中沒有 prototype 連線。
政策題（P-1～P-10）：…
已抽出、一致的規則（27 條，展開可看）
  L2-1 畫面 390×844；頂部 Status Bar（含瀏海）＋Top bar/Web page
  L3-1 左右邊距 16（Space/400）；L3-2 卡片內距 24；…
  L7-1 主按鈕：Button type=Active，每畫面 1 個，固定底部，從既有 instance 取主元件
回覆「全部確認」，或指出編號修改。
```

## 8. 限制與待驗證

- **抽取成本**：大型頁面（M0：約 5,600 個 instance）不能整頁讀；必須先在第 1 輪縮小到選定的參考畫面，每批回傳在 20 KiB 內（CAP-05）。
- **角色推測可能出錯**：文字與顏色的「角色」是依位置、字級推測的，所以要讓使用者確認，低信心項目一律轉成問題。
- **門檻未經實測**：信心分級的 3 處／90%／70% 是專案預設，需要用真實任務校正。
- **使用者負擔**：規格表太長會讓人直接按「全部確認」。以異常優先、高信心摺疊來控制；實測時記錄每個 run 的提問數、確認時間、Validate 發現的 findings 數、被略過的決策數，比較有無規格表的差異。
- **與 spec 的關係**：規格表整合了 §6.6 pattern、§7.4 決策、v1.4 可及性預檢；採用時要一起修改這幾節，避免重複的規則來源。
